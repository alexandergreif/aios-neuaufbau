# Prepare a Brief

Read the [shared rules](../../rules/core.md) to the extent needed for preparation. This skill supplements them and grants no new authority.

Adopt goals, decisions and limits already stated. Clarify only essential gaps. Ask a targeted question when the result, acceptance, authority or a genuine conflict of goals does not allow a solid formulation. Do not invent sources, paths, commitments or rights. An unknown working location can appear in the resulting brief as a starting step still to be checked. If a source needed for the task is missing, name the gap and ask how to proceed. Do not include a blanket permission to proceed without that source.

Output a copyable prompt for the requested client, for both clients only on request. Keep the content and authority of both versions identical. The prompt names the result, observable acceptance, limits and a known starting point or the needed inventory check. Preserve existing changes when the task works on existing files. Carry over external write, send, publish, delete or production rights only from the concrete user task. A diagnosis confirmation needed for bug fixes still applies, unless it is already in place.

For explicitly longer autonomous work, add permitted means, interim status updates, genuine blockers and a stop condition. A blocker is not an achieved result. Only include a time, cost or token budget if it is specified or decisive for the task. Check the actual capabilities of the target client before recommending a special input form. A normal prompt body must remain usable even without a goal function. Do not force a `/goal` command.

Output the finished prompt in a labeled code block and briefly state the needed assumptions below it. If a solid prompt is not yet possible, ask the decisive follow-up question instead of presenting placeholders as finished. Preparation alone does not start a task or an autonomous run and does not change files or external systems. If the user has also explicitly requested the subsequent execution, handle this follow-up task after the preparation within the already authorized scope. Do not skip required diagnosis approvals or source clarifications. Merely formulating an executable prompt is not such a request.

[Synthetic test cases](references/test-cases.md) serve later behavior checks. Their inclusion is not proof of passed model tests.
