# Use Case Concept

Follow the [core rules](../../rules/core.md), [storage](../../references/storage.md) and for lasting facts [profile and knowledge](../../references/profile-and-knowledge.md). Use only the sources approved for the task. If a needed original requirement, decision or technical source is missing, name the gap, ask first about how to proceed and wait for the decision before continuing on a limited basis.

Record the original requirements with source anchors. Keep them separate from interpretations, drafts and later proposals. Describe the problem, target audience, desired benefit and a concrete case from the trigger through inputs, processing and human decisions to the result. Show the roles involved, data sources, connections, approvals and error cases. Make risks and limits visible. Contradictions between requirements and feasibility stay open until they are resolved.

Check decisive technical statements against current, suitable original sources. Distinguish between evidenced as available, to be set up, to be developed and still to be checked. A documented API endpoint or code path does not prove authorization or that it works in the specific environment. Formulate a limited pilot with sample data, prerequisites, responsibilities, measurable criteria and a decision after the evaluation. Commit to effort, dates and benefit only with a solid basis.

Choose the short version, long version and output format according to the task. If both versions are needed, the workflow, limits and commitments must match. An old document renderer is not a default to use without verification. Creating the concept starts neither implementation nor sending. Lasting knowledge notes follow only after the confirmation required for that.

[Synthetic test cases](references/test-cases.md) describe later behavior checks, not passed model tests.
